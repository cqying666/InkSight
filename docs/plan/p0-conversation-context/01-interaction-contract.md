# P0-01 自然语言交互规则与示例

状态：待用户验收。版本0.1，2026-09-15。本文件定义期望行为，不代表产品已经实现。

## 1. 背景与目标

作者通过自然语言从对标拆解进入候选讨论，不能先学会“聚焦、选定、保存”的按钮流程才能继续。Agent负责理解目标、识别方向版本、保留相关依据和作者决定。

本期产品决定：P1取消【比较候选方向】按钮；需要比较时由作者直接提问。其他既有按钮若保留，只作为可选快捷方式，不是进入上下文的前提。P0不实际删除按钮。

保留两项设计：轻量反馈当前理解；只有存在会影响结果的真实歧义时才澄清。不能因为新贴正文或方向未点击保存，就要求作者再次确认是否允许分析。

## 2. 四种信息状态

| 状态 | 含义 | 默认处理 |
|---|---|---|
| 当前讨论对象 | 本轮正在讨论的一个或多个候选版本 | 可以临时切换；不自动替换已选方向 |
| 已选方向 | 作者明确决定采用的具体版本 | 持续作为创作基础；不等于已经写入作品正文 |
| 作者有效要求 | 作者明确给出的题材、结局、人物行动等限制 | 保留原句、适用方向及生效/被替代关系 |
| 待选建议 | 模型提出、作者尚未采纳的修改或情节 | 可以讨论，不得成为已确认设定 |

比较对象与创作对象分开：比较A和C时可以保留“原来选的是B”，不能把A/C全部当正式设定。选定v1、聚焦v3同时存在时，当前请求决定讨论哪一版，界面反馈须使用明确版本。

## 3. 自然语言示例与期望行为

| 编号 | 用户表达 | 期望状态与动作 | 轻量反馈示例 |
|---|---|---|---|
| NL-01 | 继续聊第二个方向 | 唯一定位后聚焦第二个，原选定不变 | 我们先讨论第二个职场方向。 |
| NL-02 | 就用第二个 | 唯一定位后选定并聚焦该版本 | 好，以第二个方向v1作为接下来的创作基础。 |
| NL-03 | 就用第二个，结合刚才第一章分析往下讨论 | 原子记录选择，获取相关导语/章节报告并回答 | 沿第二个方向继续，并结合刚才第一章的结构分析。 |
| NL-04 | 第二个可以，但不要靠男二解决问题 | 按“接受该方向并新增明确约束”处理；已有冲突再澄清 | 好，保留这个方向，并让女主主动解决问题。 |
| NL-05 | 第二个好像可以，要不要用它？ | 这是征询意见；只讨论优缺点，不更改选定 | 可以从人物动力和后续展开比较它的取舍。 |
| NL-06 | 比较第一和第三个 | 绑定两者具体版本，给比较依据；不代替作者选 | 比较这一组的第一和第三个，当前已选版本先保留。 |
| NL-07 | 这几个哪个更合适？ | 若只存在一组清楚的当前候选，比较该组；存在多组实质歧义才问 | 你指最初的三条方向，还是后来两版寿宴方案？ |
| NL-08 | 我还是用修改之前的第二版 | 找回唯一的历史v2，选定并聚焦v2 | 回到寿宴方向v2，后面的v3保留为历史参考。 |
| NL-09 | 修改第二个，让女主更主动 | 以指定版本形成新建议/版本；不静默替换已选 | 我先给这个方向的修改建议，原已选版本保持。 |
| NL-10 | 就按刚才修改后的版本来 | 若指代唯一，采纳对应版本，记录确认来源 | 好，接下来以修改后的v3为准。 |
| NL-11 | 保留截图取证这个建议，别用搬家那个 | 只采纳被明确点名的建议，其他不连带采纳 | 保留主动取证，不采用搬家情节。 |
| NL-12 | 结局改成和解，不再要求不复合 | 明确替代同一方向旧约束，保留旧记录 | 结局要求已改为和解，其他有效限制继续保留。 |
| NL-13 | 让他们和好，但保持之前所有要求 | 若与“不复合”冲突且无法判明，先澄清；不改状态 | 之前要求不复合，这次是想正式改为和解吗？ |
| NL-14 | 第一章重新贴在下面，分析大概念 | 绑定新原文与新任务，不沿用旧导语；无需保存许可 | 这次分析你新贴的第一章。 |
| NL-15 | 这段不要了，换一条完全不同的方向 | 明确放弃当前方案时标记不再采用；生成新方向不自动选定 | 放弃这条方案，下面给你新的候选。 |
| NL-16 | 比较这两个版本，但不要改我的选择 | 比较指定版本，选定状态不变 | 只比较v1与v3，仍保留你选定的v1。 |
| NL-17 | 保存这个方向 | 对象清楚时保存会话成果；不能声称已写入作品 | 已保存这个版本为会话成果。 |
| NL-18 | 把选定方案带到工作台 | 明确目标后进入作品衔接；涉及覆盖已有稿件需明确目标 | 将已选版本带入工作台，并保留来源。 |

NL-04的处理依赖完整语境：若作者是在引用别人的评价，或随即说“暂时不选”，不能按确认处理。上表是语义测试样例，不是简单关键词正则表。

## 4. 指代解析规则

依次使用：明确的标题/版本/候选标识；本轮明确引用的候选组；最近正在讨论且唯一可指的对象。只有作者说“已选定的”才应直接指向selected；“正在讨论的”指向focused。

“第二个”对应候选组的展示顺序，不是数据库全局第二条。若有两组均合理，先询问；不能永远取最新一条助手消息里的第二个，也不能把存在旧候选本身当成必须询问的理由。

用户在一句话中先选定、再提出讨论要求，只要两部分明确，就先记录选择，再执行讨论；后续模型工具失败不应抹掉已明确表达的作者选择。若选择本身不明确，澄清前不改变状态。

## 5. 反馈与异常

- 正常确认用一句自然语言回应，不弹确认框、不要求再点选定/保存。
- 页面持续显示当前讨论对象；本轮回答可展开查看对应报告和作者要求。
- 回复后的“你更喜欢哪种写法？”是可选反馈，不把已交付答案标成任务未完成。
- 容量问题由系统先自动整理；只有必须改变范围时说明原因和可继续的选择，不要求重贴已保存资料。
- 比较结果解释优缺点与适用条件。除非作者明确要求推荐，否则不代替作者决定；推荐也不能自动改变selected。

## 6. 现状差距及下一阶段边界

现有commands.ts只识别少数独立选择句，混合要求和跨组指代覆盖不足；比较按钮仍发送泛指文本。P1应按本契约实现自然语言状态转换与反馈，再取消比较按钮。P0仅明确规则和验收，不修改当前功能。
