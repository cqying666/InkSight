## 1．项目目标与决策前提

### 用户已经明确的目标

完善 InkSight 本身是行动主线，完善的明确目的是 AI 产品经理求职展示：丰富有真实依据的简历项目经历，并在面试中演示产品、解释设计逻辑及个人贡献。

因此，功能取舍同时考虑：

1. 是否解决真实的网络短篇创作问题。
2. 是否能展示场景判断、Agent 设计、RAG、上下文管理、人机协作、效果评测与持续迭代能力。
3. 是否能形成可演示、可检查、可解释的结果，而不只是增加 AI 功能按钮。

不要将求职展示降为偶然的附带成果，也不要为覆盖技术名词而无依据地扩展功能。个人项目不能冒充商业规模、团队协作经历或已经验证的业务收益。

### 当前阶段

用户要求先理清方案、制作过程和整体逻辑。本文不意味着已授权启动整个平台重构，也不意味着讨论中的建议都已确定。具体实现范围、优先级和验收数值仍需后续确定。

## 2．首页 Agent 的四类能力范围【用户已确认】

首页大输入框应成为整个创作 Agent 的入口：理解自然语言目标，根据当前作品资料、任务状态和可用能力决定行动，而非仅按关键词跳转到固定功能页。

| 能力 | 用户目标 | 建议交付形态 |
|---|---|---|
| 素材转核心梗与框架 | 根据提供的素材提炼核心梗，选择合适框架 | 核心梗候选、框架推荐、适配理由与局限 |
| 对标文拆解与二创方向 | 分析剧情、大概念、人设等，并提出二创方向 | 带原文依据的拆解、可迁移机制、有实质变化的新方向 |
| 写作答疑与审查 | 审查导语、大纲、细纲乃至全文，提出修改意见 | 问题位置、依据、影响、修改建议与取舍 |
| 小说剧情探讨 | 讨论人物选择、剧情分支和后续发展 | 候选走向及后果分析，由作者决定是否成为正式设定 |

范围说明：

- 四类是用户确认的产品能力方向，不等于第一批全部做到同等深度。
- 审查、讨论、建议与实际修改、保存作品是不同操作，应明确区分。
- 用户并未要求第一版自动写整本小说或自动投稿。
- “大纲诊断与局部修订 Agent”是前期提出的优先验证切入点，不应覆盖掉用户后来明确的四类总体范围；优先级待确定。

## 3．现有能力与首页限制【讨论期间的代码检查结论】

以下来自本次对话中的静态代码检查，没有完成全面运行验收。仓库存在其他进行中的修改，后续必须复核最新实现，不能把本节作为永久现状。

### 首页

`src/components/home/CoachInput.tsx` 中的固定技能选项为：拆文、写导语、大纲生成、细纲生成。它们是应用内功能选项，不是动态读取本地 Codex 技能列表。

`src/app/(workspace)/page.tsx` 的提交逻辑：

- 显式选择技能时，进入对应生成、分析或工作台流程。
- 细纲生成入口先跳到工作台，依赖已有大纲。
- 不选择技能时，由 `src/lib/home/intent-router.ts` 进行关键词、文本分隔和长度判断，不调用 LLM 理解意图。
- 自然语言路由包括全文拆解、导语分析、导语分析加二创方向、导语生成。
- 未识别的请求主要跳转到上传页、工作台或趋势页，默认进入工作台。
- 自然语言表达与显式选择技能并不完全等价。
- 首页没有承接开放式多轮创作讨论的完整会话链路。含“大纲分析”的请求还可能因长度被分到导语或全文分析。

### 工作台与 AI 能力

- 工作台已经存在 AI 教练，不应声称整个产品都不能讨论创作问题。
- `src/components/write/AICoachPanel.tsx` 按面板调用 `/api/outline-coach` 或 `/api/coach`。
- 大纲教练预先读取当前大纲、关联资料、最近拆文摘要并检索素材，再调用模型回答。
- 该路径的资料读取步骤由代码固定安排；不能因为使用 Pi Agent 框架或展示工具状态，就宣称已经实现模型自主选择行动的闭环。
- 已有结构化分析、素材分类、语义检索、部分超时降级、模型管理、调用日志和产品指标设计，不能将整个项目仅描述为 Vibe Coding 页面原型。

### RAG 与检索

- `src/lib/ai/embedding.ts` 使用 Transformers.js 加载中文 BGE 模型生成向量；`src/lib/material/zvec-index.ts` 使用 Zvec 索引和搜索。
- 大纲教练把检索资料放入模型上下文，属于初步 RAG 应用。
- 向量无结果或失败后回退关键词检索，不等于混合召回、融合排序和语义重排都已实现。
- 当时实现先在共享向量索引召回，再按用户数据过滤；需复核用户命名空间、候选占位和作品范围问题。此观察不等于已证实数据泄漏。
- 接入向量数据库不等于已经证明知识库成功；需要验证检索准确性、证据使用、更新一致性及最终用户收益。

### 评测证据的限制

当时读取的 `tests/consistency-report.md` 记录了三篇文章、每篇一次运行，并包含解析失败，却显示总体一致性 100%。单次运行不能证明重复稳定性，失败样本也必须计入相关成功率。该旧报告不可直接用于简历效果宣称。

仓库已有人工盲测流程设计，但流程文件不等于已经完成盲测。后续应核对原始记录。

## 4．Agent 的整体逻辑【设计共识】

### 意图不是功能标签

用户说“这个女主的行为不合理”，系统应理解目标、对象、缺少的信息、期望交付和修改限制，而非只判断是否命中“拆文”按钮。

未对应现有按钮的请求分为三类：

1. 可以通过阅读、理解与讨论回答。
2. 可以组合现有能力完成。
3. 缺少必要信息或能力，需要补充、缩小范围或说明无法完成。

模型能生成文字不等于系统能可靠完成该任务。工具未开放的能力不能靠提示词假装已经执行。

### 目标驱动闭环

理解目标与约束 → 查看当前状态与必要作品资料 → 判断信息缺口 → 按需检索、调用能力或询问 → 执行 → 检查结果并更新状态 → 继续、调整、交付或停止。

“当前环境”主要包括上传文本、作品及版本、已确认设定、用户约束、可用工具、执行进展和错误结果。

- 简单问题不必生成完整计划。
- 不要求每一步重新检索全部知识或记忆。
- 成熟固定流程可以作为自主 Agent 调用的能力，形成外层决策、内层稳定执行的组合。
- 检查应围绕用户目标和约束，不以模型自称满意为唯一依据。
- 任务完成、信息不足、需要作者裁决、超出重试或成本预算，都应有相应结束或暂停方式。

### 示例：文章中段拖沓

用户要求检查事件与情绪节奏、保留结局。

1. 读取文章和要求，明确目标是定位拖沓原因并提出改法。
2. 利用拆文能力定位重复场景，给出原文依据。
3. 按需查询冲突递进、情绪压放、题材节奏方法。
4. 提出合并场景、增加信息、推动人物选择等方案；在授权范围内生成候选修订。
5. 检查是否误删伏笔、破坏人物动机或改变结局。
6. 如发现新问题，调整方案；最后交付差异、依据和未解决问题。

### 接入原则【建议，尚未实施】

本地 Markdown → 解析正文与字段 → 保留来源、版本和适用范围 → 按语义组织知识单元 → 建索引 → 按任务检索 → 更新时同步。

- 知识保存在数据层，代码负责导入、更新、检索和使用，不把每条知识写死在业务代码里。
- 这不是训练模型参数，也不要求每次将全库塞入上下文。
- 使用现成 Zvec 不影响产品价值；重点是数据组织、检索策略、评测和使用效果。
- 不必限定检索大纲文件夹。大纲诊断还需要人设、冲突、信息差、情绪递进、伏笔、题材和导语兑现等方法。
- 框架是有适用条件的参考，不应把某个模板当成所有作品的唯一正确结构。
- 原始来源、模型归纳、人工确认结论需区分。检索到资料不等于资料支持了最终结论。

### 建议的方法内容结构

每条方法包含：适用情况、必要输入、操作步骤、质量标准、正反案例、限制与失败回退、来源依据。

教学提示词需先理解、筛选，才能整理为经确认的操作模板；不能让任意检索文本改变 Agent 的行为权限。

## 6．Prompt、Skill、Workflow、Tool 与 Agent

以下是本产品讨论采用的概念分工，不假定所有框架都采用相同定义。

| 概念 | 职责 | 拆文中的例子 |
|---|---|---|
| Prompt | 指导一次模型调用如何处理输入、输出结果 | 剧情分析、人设分析提示词 |
| Skill | 可复用的任务方法包，包含适用条件、步骤、模板和规范 | 对标文拆解技能 |
| Workflow | 固定或受控的步骤顺序、依赖、数据传递与异常处理 | 读取→剧情／大概念／人设分析→汇总检查 |
| Tool | Agent 可调用的动作接口 | 运行拆文、读取作品、检索知识 |
| Agent | 根据目标和反馈决定下一步行动 | 判断是否需要拆文，调用后决定补充分析或生成新方向 |

拆文可以同时是 Skill 和 Workflow，两者不互斥：一个拆文 Skill 可以规定方法，由固定 Workflow 执行，首页 Agent 通过工具调用。

若仅一次模型调用输出剧情、大概念、人设三个部分，不能仅凭三个输出栏目称为多步骤 Workflow。也不必为了名称强行增加调用次数。

若希望只分析人设而不运行完整拆文，需要实际提供对应调用能力。

## 7．知识、作品资料与记忆

| 信息 | 示例 | 管理原则 |
|---|---|---|
| 工作记忆／任务状态 | 本次目标、计划、工具结果、待解决问题 | 随任务保存和更新 |
| 作品资料与正式设定 | 女主不知道真相、已确认结局 | 按作品与版本读取，维护事实约束 |
| 作者长期记忆 | 追妻题材默认不复合、偏好克制对白 | 跨任务使用，有范围，可修改删除 |
| 外部领域知识 | 创作方法、案例、框架 | 按需检索并保留来源 |

RAG 是检索增强生成的方法，不是一种信息来源；既能用于知识资料，也能用于记忆。长期记忆不要求必须由 Agent 自动形成，用户明确要求保存的偏好也可以成为长期记忆。

关键作品约束不能因为向量搜索未召回就被忽略。信息来源、用途、更新权限和优先关系需要明确。

### 网页反馈与开发侧调试

- InkSight 网页承担真实使用、追问、采纳、拒绝、保存设定与偏好。
- 开发对话承担方法调整、功能开发、失败分析和评测。
- 在网页反复纠正、仅保存聊天记录，都不天然构成长期记忆。
- 在 Codex 对话中提出的规则，也不会自动同步到 InkSight。

建议的记忆链路：捕获反馈 → 分类 → 必要时形成候选记忆 → 确认范围 → 持久化 → 后续读取 → 更新或删除。

第一版可考虑提供“仅本次生效”“保存为本作品设定”“记住为我的创作偏好”，之后再考虑自动提取候选偏好。此方案尚未确认实施。

“你总是套三幕结构”可能是产品方法缺陷，应作为失败案例评估；不能自动升级成全体用户规则。

## 8．可靠性、评测与求职展示【后续设计建议】

### 需要验证的层次

1. 检索：正确证据是否被找到，是否误用旧资料，是否能判断资料不足。
2. 任务：是否满足目标、保持硬约束、处理异常，完成成本与耗时如何。
3. 用户：建议是否被采纳，到达可接受版本的总时间与返工是否减少。

文学质量、事实一致性和用户偏好不能混成一个“准确率”。模型自检和评分可以辅助，不能代替人工与真实用户反馈。

对照思路：同一模型直接处理 → 固定检索增强流程 → 有限自主 Agent。尽量控制其他条件，保留未参与调优的验证样本。若 Agent 没有收益，应据此调整方案，而非强行增加复杂度。

前期提出过约 30—50 个检索问题、20—30 个修订任务作为启动规模，以及先访谈少量创作者。这些只是建议，不是已完成数据、行业标准或已确认排期。

### 可演示的能力证据

- 明确的用户问题与任务成功标准。
- 选择 Prompt、RAG、Workflow 或 Agent 的理由。
- 一次真实任务中读取的资料、执行动作、结果检查和调整。
- 修改差异、人工介入、未完成原因和版本管理。
- 真实对照数据与失败案例复盘。

不要将聊天次数、生成字数或框架接入本身当作最终业务成果。不宣称保证签约、爆款或求职 Offer。
